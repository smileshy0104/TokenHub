# TokenHub 用于公司研发中心 AI 监控与治理的落地评估

> 本文评估 TokenHub 是否适合用于“公司研发中心各个团队”的统一 AI 接入、使用监控、成本治理和安全运营，并给出上线前需要补齐的能力、推荐架构和分阶段实施方案。
>
> 评估基于当前仓库中的前端控制台、Go 后端、部署配置、管理员指南、成本治理、健康检测、内容安全和插件实现。文中会明确区分“已经具备”“部分具备”“目前只是配置展示”以及“尚未完整实现”的能力，避免将控制台字段误认为已经生效的运行时策略。

---

## 1. 执行摘要

### 1.1 总体结论

TokenHub 当前适合作为：

> **研发中心 AI 使用统一接入与成本治理试点平台。**

它已经具备 AI Gateway 的主要基础能力：

- 统一兼容 OpenAI、Anthropic、Gemini 等调用协议。
- 集中管理 Provider、Provider Resource、模型库存和路由。
- 按团队、项目、用户和 API Key 管理访问权限。
- 记录请求、Token、成本和 Provider 路由归因。
- 支持额度、并发、成本和内容安全策略。
- 支持 OAuth/OIDC 企业登录。
- 支持账单同步、成本对账、审计和通知渠道。

但是，如果目标是直接承担整个研发中心的企业级 AI 生产运营平台，当前仍有几个关键短板：

1. 健康检测还不完全等于端到端 AI 服务探测。
2. 告警规则尚未形成完整、统一、自动执行的告警引擎。
3. 成本中心预算和真正能够阻断请求的运行时预算存在区别。
4. Prompt、Response、工具参数和文件数据治理还需要进一步细化。
5. 企业身份目录同步和权限生命周期还不够完整。
6. 当前单机 SQLite 部署不适合研发中心长期多团队高可用运行。
7. 外部命令型插件目前不能在 TokenHub 生产运行时执行。
8. 当前偏重调用量、成本和可用性监控，AI 质量和业务效果监控不足。

因此，建议采用“先试点、再平台化”的路线，而不是直接把当前版本定义为全公司级 AI 生产平台。

### 1.2 建议的上线判断

| 使用阶段 | 建议 |
| --- | --- |
| 单团队或少量团队试点 | 可以使用，但应先完成安全、身份和数据保留配置 |
| 研发中心 1～5 个团队内部生产 | 可以在 P0 能力完成后使用 |
| 多团队高并发统一入口 | 需要 PostgreSQL、Redis、多副本和集中观测 |
| 全公司级 AI 平台 | 当前不建议直接承担，应先补齐自动告警、预算、目录同步和质量评测 |
| 严格财务结算平台 | 当前成本数据仍应视为估算和对账依据，不应直接替代财务系统 |
| 高敏感数据生产平台 | 需要先完成数据分类、Prompt/Response 治理和 Provider 数据边界建设 |

## 2. 目标场景和范围

本文假设的目标场景是：

```text
公司研发中心
├── 平台研发团队
│   ├── 网关平台项目
│   └── 内部工具项目
├── 算法团队
│   ├── 评测平台项目
│   └── 知识库项目
├── 应用研发团队
│   ├── 客服助手项目
│   └── 研发助手项目
└── 数据与基础设施团队
    ├── 数据分析项目
    └── 自动化 Agent 项目
```

各团队希望通过 TokenHub：

- 使用统一 API 地址和 SDK。
- 使用经过批准的模型。
- 不直接接触 Provider 密钥。
- 查看团队、项目和个人用量。
- 分析成本和资源使用情况。
- 对高成本或高风险模型进行审批。
- 监控 Provider 可用性、延迟和错误。
- 对 Prompt、敏感数据和外发内容执行安全策略。
- 在权限边界内自助管理项目和 API Key。

本文重点评估以下方面：

- AI 资源管理。
- 统一接入和请求路由。
- 团队、项目和权限治理。
- 使用量、成本和预算治理。
- 健康检查和自动告警。
- 内容安全和数据隐私。
- 企业身份认证。
- 高可用和多实例部署。
- 插件扩展能力。
- AI 质量和效果监控。

## 3. 当前已经具备的能力

## 3.1 统一 AI 接入

TokenHub 可以将多个上游模型服务统一暴露给业务团队。当前已覆盖或设计支持：

- OpenAI-compatible API。
- Anthropic Messages。
- OpenAI Responses。
- Embeddings。
- Rerank。
- 图片生成和编辑。
- Gemini 原生接口。
- Audio、Transcription 和 Translation 等媒体接口。
- TokenHub 专有的结构化接口。

业务团队可以统一使用：

- TokenHub API Base URL。
- Project API Key。
- TokenHub 模型名称。
- 标准 SDK 调用方式。

团队不需要直接保存或分发每个 Provider 的 API Key、Base URL 和协议细节。

## 3.2 Provider、账号资源和多线路

当前已经具备以下 AI 资源模型：

```text
Provider
  └── Provider Resource
        └── Provider Model

对外 Model
  └── ModelRoute
        └── Provider / Resource / Provider Model
```

其中：

- **Provider**：上游服务渠道，例如 OpenAI、Anthropic、Gemini、DeepSeek、Qwen 或兼容服务。
- **Provider Resource**：Provider 下的实际 API Key、订阅账号、PAT、区域资源或资源池成员。
- **Provider Model**：上游真实模型库存。
- **Model**：TokenHub 向调用方公开的统一模型名称。
- **ModelRoute**：将统一模型映射到某个 Provider、Resource 和上游模型。

这种分层适合研发中心统一管理：

- 多家供应商。
- 同一供应商的多个账号。
- 不同区域和环境。
- 不同成本档位。
- 内部模型和外部模型。
- 生产、测试和合规专用线路。

## 3.3 路由和故障转移

当前支持或设计支持：

- 路由优先级。
- 流量权重。
- Project 作用域。
- 路由标签。
- 粘性会话。
- Provider Resource 冷却。
- 非流式请求故障转移。
- 健康和冷却状态过滤。
- Provider、Resource、Model 和协议能力过滤。
- 全局、项目和 API Key 级作用域路由策略。

路由策略可以采用：

- `priority_only`
- `priority_weighted`
- `balanced`
- `adaptive`
- `cost`
- `quality`
- `inherit`

需要注意，权重和优先级只会影响仍然合格的候选线路，不能绕过：

- Provider 禁用状态。
- Resource 禁用状态。
- 健康状态。
- 项目模型权限。
- 协议能力不匹配。
- 作用域路由策略。
- 资源冷却和并发限制。

## 3.4 团队、项目和 API Key 治理

当前已经具备企业组织治理的主要实体：

- 后台用户。
- 团队。
- 项目。
- 项目成员。
- Project API Key。
- Key 归属用户。
- 角色和项目角色。
- 模型访问权限。
- 额度策略。
- 成本中心。
- 审批记录。
- 审计记录。

可以表达类似下面的组织结构：

```text
研发中心
├── 平台研发团队
│   ├── AI Gateway 项目
│   └── DevOps Agent 项目
├── 算法团队
│   ├── 模型评测项目
│   └── RAG 项目
└── 应用研发团队
    ├── 研发助手项目
    └── 内部知识库项目
```

业务调用凭证属于 Project，而不是直接属于某个 Provider。这样可以集中管理：

- API Key 状态。
- 模型白名单。
- 来源 IP 白名单。
- 日/月请求和 Token 限额。
- 用户归属。
- 项目成本和用量。

## 3.5 用量和成本归因

当前支持或已经展示以下维度：

- 模型。
- Provider。
- Provider Resource。
- Project。
- Team。
- User。
- API Key。
- Cost Center。
- Token 类型。
- 请求状态。
- 估算成本。

这可以回答：

- 哪个团队调用量最大？
- 哪个项目成本最高？
- 哪个模型最贵？
- 哪个 Provider 使用最多？
- 哪些 Key 接近限额？
- 哪些项目错误率较高？
- 哪些团队集中使用高价模型？

但这些数据目前更偏向管理报表和成本治理，不等同于完整的 AI Observability 平台。

## 3.6 额度和并发治理

额度策略支持以下作用域：

- `global`：全局。
- `project`：项目。
- `team`：团队。
- `api_key`：API Key。
- `user`：用户聚合。

支持的限制包括：

- RPM。
- TPM。
- 日请求数。
- 月请求数。
- 日 Token 数。
- 月 Token 数。
- 日成本 USD。
- 月成本 USD。
- 最大并发数。

同一请求可能同时受到多个层级约束，系统按照适用的最严格正数限制执行。用户作用域会聚合该用户所有归属 Key 的用量，Key 轮换不会重置用户额度。

请求流程包含：

1. 鉴权和项目解析。
2. 解析适用额度策略。
3. 预留 Token、请求和并发容量。
4. 执行 Provider 请求。
5. 根据实际 Usage 进行结算、退款或调整。

## 3.7 内容安全基础能力

当前内容安全 Guardrail 已经接入主要网关请求链，支持：

- 关键词匹配。
- 正则表达式匹配。
- 敏感数据识别。
- Qwen3Guard 模型检测接入点。
- `audit`：允许请求并记录。
- `mask`：将命中内容替换为 `[REDACTED]`。
- `block`：拒绝请求。
- 全部项目或指定项目绑定。
- 策略测试面板。
- 请求前检查。

动作优先级为：

```text
block > mask > audit > allow
```

当前还应注意：

- Provider 响应检查不是完整覆盖范围。
- 工具参数和任意 JSON 深层字段不能假定全部检查。
- 二进制文件、图片和音频内容需要单独评估。
- 需要代码语义分析的敏感信息不属于简单文本匹配范围。
- 远程 Qwen3Guard 服务的数据传输、日志和保留策略不由 TokenHub 自动管理。

## 3.8 OAuth/OIDC 企业登录

当前支持或提供模板：

- 通用 OIDC。
- 通用 OAuth2。
- Google。
- Microsoft Entra ID。
- Okta。
- Keycloak。
- GitLab。
- 钉钉。

正式上线前仍需要补充企业目录组同步、离职用户自动禁用和角色映射策略。

## 3.9 成本账单和对账

当前成本治理区分：

1. 客户侧估算费用。
2. Provider 本地估算成本。
3. Provider 外部账单金额。

已经具备或正在接入：

- 影子价目。

当前具备：

但是，告警规则的自动计算和自动通知仍需要进一步完善，详见后文。

## 4. 当前不足和风险

## 4.1 健康检测不等于端到端 AI 健康监控

这是当前最需要注意的问题。

当前默认 Monitor 的基础判定主要是：

| 对象 | 当前基础判断 |
| --- | --- |
| Provider | 对象存在且 `status=active` |
| Provider Resource | 对象存在且 `status=active` |
| Model | 至少存在一条启用 ModelRoute |

因此，“健康检测通过”不能充分证明：

- Base URL 可达。
- 凭据仍然有效。
- 上游模型真实存在。
- 模型能够正常推理。
- 流式输出正常。
- Embedding、Rerank、图片和音频接口正常。
- 上游没有持续返回 429、5xx 或超时。
- 实际延迟和首 Token 时间符合 SLA。

当前健康检测更接近：

> 配置对象和数据库状态检查。

### 建议增加分层探测

```text
L1 配置状态
  ↓
L2 网络连通性
  ↓
L3 鉴权验证
  ↓
L4 模型存在性和能力验证
  ↓
L5 轻量真实推理
  ↓
L6 流式、Embedding、Rerank 和媒体协议验证
```

建议每层都记录：

- Probe 类型。
- Probe 时间。
- 延迟。
- HTTP 状态。
- 错误分类。
- Provider Request ID。
- 是否计入正式用量。
- 是否产生真实成本。
- 是否允许发送测试内容。

探测应支持：

- 测试模型选择。
- 最大 Token 限制。
- 每个 Provider 的最小成本。
- 超时和重试策略。
- 测试租户或专用项目。
- 失败冷却和恢复。
- 与正式流量分开统计。

## 4.2 告警规则尚未形成完整自动规则引擎

当前已经有：

- 告警规则资源。
- 告警事件。
- 通知渠道。
- 通知记录。

但不能简单假设告警规则中的所有字段都已经由统一运行时引擎自动执行。特别是以下字段仍需要确认实际执行路径：

- 指标。
- 阈值。
- 事件代码。
- 严重级别。
- 通知渠道。

因此，当前可能出现：

- 配置错误率阈值，但没有持续窗口计算。
- 配置 P95 延迟阈值，但没有自动产生告警。
- 填写通知渠道，但新事件不一定自动投递。
- 停用规则，但特定代码路径仍然直接产生同类事件。
- 告警事件生成和通知成功之间没有自动闭环。

### 推荐的告警引擎模型

```text
指标采集
  ↓
窗口聚合
  ↓
规则评估
  ↓
触发 / 恢复
  ↓
去重 / 抑制 / 合并
  ↓
通知路由
  ↓
告警和投递记录
```

至少应支持：

- 错误率。
- P50、P95、P99 延迟。
- 429、5xx 和超时。
- Provider 不可用。
- Resource 冷却。
- Model 无可用路由。
- Token 消耗异常。
- 成本突增。
- 日/月额度接近上限。
- 内容安全拦截率异常。
- 告警恢复。
- 去重和冷却时间。
- 按团队、项目、Provider 和模型路由通知。

## 4.3 访问安全配置存在“保存但未统一执行”的区别

“安全策略”页面中的访问安全字段包括：

- `mask_prompts`。
- `ip_allowlist`。
- `error_passthrough`。

这些字段目前主要作为管理资源保存和展示，不能全部视为已经接入统一网关执行链的全局安全边界。

需要区分：

### 已接入运行时的能力

- API Key 自身的 IP 白名单。
- RBAC 和管理 Session。
- CORS。
- 可信代理配置。
- Provider SSRF 防护。
- 内容安全 Guardrail。
- 凭据加密。

### 不能仅凭页面配置认为已经全面生效的能力

- 全局 Prompt 审计脱敏。
- `security-policies` 资源中的全局 IP 白名单。
- 所有错误响应的统一透传策略。

正式上线时，应分别验证每个字段对应的后端执行入口和测试覆盖，而不是只检查页面保存是否成功。

## 4.4 成本中心预算和运行时预算不是一回事

成本中心用于：

- 部门归属。
- 负责人管理。
- 成本报表。
- 项目和团队归因。
- 预算展示或治理配置。

真正能够在请求准入阶段阻断调用的运行时预算，使用独立的预算资源和 enforcement 配置。

因此：

> 在成本中心表单中填写 `monthly_budget_usd`，不能自动证明请求会在达到金额后被阻断。

建议统一为明确的预算模型：

```text
Budget
├── 作用域：全局 / 成本中心 / 团队 / 项目 / Key / 用户
├── 周期：日 / 月 / 自定义周期
├── 币种和汇率
├── 预警阈值
├── 软限制
├── 硬限制
├── 超额动作：告警 / 限制高价模型 / 阻断
├── 豁免角色
└── 时区
```

## 4.5 团队级 AI 使用分析仍不够完整

当前报表可以查看很多用量和成本维度，但还需要更完整的研发中心分析。

### 团队指标

- 团队请求数。
- 团队 Token。
- 团队估算成本。
- 活跃用户数。
- 活跃项目数。
- 人均调用量。
- 人均成本。
- 增长趋势。

### 项目指标

- 模型分布。
- Provider 分布。
- 成功率。
- P50/P95 延迟。
- 429/5xx/超时比例。
- 缓存命中率。
- 单请求平均成本。
- 用户活跃度。

### 模型指标

- 模型成功率。
- 首 Token 延迟。
- 输出吞吐。
- 上下文长度分布。
- 输入和输出 Token 比例。
- 缓存读写比例。
- 单模型成本趋势。
- 工具调用成功率。

### 异常指标

- 请求量突然增加。
- 成本突然增加。
- 单 Key 异常高频。
- 夜间异常调用。
- 大量高价模型调用。
- 某 Provider 成功率明显下降。
- Prompt 拦截率异常升高。
- 某项目连续失败。

## 4.6 模型访问审批和权限生命周期不够完整

当前已有部分审批能力，但公司研发中心通常需要完整生命周期：

```text
申请模型
  ↓
团队负责人审批
  ↓
安全审批
  ↓
成本审批
  ↓
自动开通
  ↓
定期复核
  ↓
到期回收
```

建议进一步支持：

- 模型访问申请。
- 高成本模型二次审批。
- 外部 Provider 审批。
- 敏感数据模型审批。
- 临时权限到期时间。
- 访问权限自动回收。
- 离职用户 Key 自动吊销。
- 未使用项目清理。
- 团队成员变化后的权限重算。
- 周期性访问复核。

以下能力通常应进入审批范围：

- 高价模型。
- 支持联网的模型。
- 支持图片、音频和文件上传的模型。
- 允许发送内部文档的模型。
- 支持工具调用或 Agent 的模型。
- 跨境 Provider。

## 4.7 企业目录集成仍需加强

虽然当前已有 OIDC/OAuth2 模板，但正式企业使用还应补充：

- 企业目录组到 TokenHub Team 的自动映射。
- 企业目录组到角色的自动映射。
- 离职和禁用用户自动停用。
- 登录时团队成员同步。
- 多身份源账号关联。
- 管理员应急账号策略。
- MFA 状态继承或强制要求。
- 会话最长时间。
- 强制重新认证。
- SAML 和 LDAP 的完整运行时支持。

当前界面可以选择 SAML 或 LDAP，并不代表这两种协议已经具备完整网页登录运行时。生产环境建议优先使用 OIDC。

## 4.8 Prompt、Response 和文件数据治理还不够细

AI Gateway 会接触：

- Prompt。
- Model Response。
- 工具调用参数。
- 代码。
- 设计文档。
- 客户资料。
- 生产日志。
- 图片、音频和 PDF。

正式使用前应明确：

- 哪些角色可以查看正文。
- 哪些角色只能查看元数据。
- Prompt 和 Response 分别保留多久。
- 是否支持按项目关闭正文记录。
- 是否支持按团队设定保留周期。
- 是否支持字段级脱敏。
- 是否记录谁查看过正文。
- 是否允许导出正文。
- 导出是否需要审批。
- 是否支持删除个人数据。
- 外部 Provider 的数据边界在哪里。
- 远程 Guardrail 服务是否保存副本。
- 文件和媒体是否进入同一套保留策略。

内容安全不能替代数据分类。对于源代码、客户数据、生产日志和商业机密，应配合企业数据分级和外发审批。

## 4.9 多实例和高可用能力需要加强

当前单机 SQLite 部署适合：

- 本地开发。
- 单机部署。
- 少量团队试点。
- 低到中等请求量。

研发中心长期多团队运行建议使用：

```text
负载均衡
   ↓
TokenHub 多副本
   ├── PostgreSQL
   ├── Redis
   ├── 对象存储
   ├── 集中日志
   ├── Metrics/Tracing
   └── 集中告警
```

需要重点验证：

- 所有副本使用同一个 `TOKENHUB_SECRET_KEY`。
- 所有副本连接同一个 PostgreSQL。
- Redis 用于高并发配额和并发 Lease 协调。
- 插件目录和插件版本在所有副本一致。
- 数据库迁移和回滚流程可控。
- 后台任务不会重复执行。
- Job 能被其他副本接管。
- 文件和备份不依赖单个容器本地磁盘。
- 负载均衡只将流量发送到健康副本。
- 宕机恢复不会丢失 Usage、审计和预算状态。

当前部分图片任务仍具有进程内排队特征，其接管能力弱于完全 Durable 的 Responses Job。不能仅因为数据库中存在任务记录，就假设执行队列已经具备完整多实例接管能力。

## 4.10 外部插件能力目前不足以支撑生产扩展

当前外部命令型插件可以：

- 安装。
- 校验。
- 查看 Manifest。
- 查看权限。
- 保存启停状态。

但不能在当前 TokenHub 生产运行时直接执行：

- 外部 Provider。
- 外部 Gateway Hook。
- 外部 Admin Action。
- 外部 Background Job。

启用这类插件后通常会进入 `failed_startup`，不会注册为可执行的 Provider、Hook、Job 或 Action。

因此，目前不能把 Plugin Devkit 中可以通过 contract test 的命令插件，等同于生产运行时可以启动的插件。

当前真正适合上传并激活的外部插件主要是：

- 纯声明式 UI Template。
- 主题 Token。
- 声明式管理页面。
- 不包含外部后端命令的 Admin UI 扩展。

如果公司希望各团队自行开发模型适配器、成本采集器、同步任务或安全扫描器，当前应优先考虑：

- 贡献到 TokenHub Core。
- 使用进程内插件。
- 通过独立外部服务和 TokenHub API 集成。
- 等待具备沙箱、权限和生命周期管理的外部插件执行能力。

## 4.11 AI 质量和业务效果监控不足

当前重点是：

- 请求是否成功。
- Token 使用量。
- 成本。
- 延迟。
- Provider 健康。
- 路由命中。
- 内容安全结果。

还缺少更完整的质量观测：

- 输出是否符合预期。
- 幻觉率。
- 代码生成测试通过率。
- RAG 检索命中率。
- 工具调用成功率。
- Agent 任务完成率。
- 用户反馈评分。
- Prompt 版本效果。
- 模型版本切换效果。
- Provider 之间的质量差异。
- 安全策略误报率和漏报率。

如果只有调用量和成本，平台只能回答：

> 团队用了多少 AI、花了多少钱。

还不能完整回答：

> AI 是否真正提高了研发效率、质量和交付速度。

## 5. P0：正式上线前必须补齐

## 5.1 企业身份和权限

至少完成：

- OIDC 接入企业身份目录。
- 目录组映射 TokenHub 团队。
- 目录组映射角色。
- 离职用户自动禁用。
- 本地应急管理员保留和审计。
- 管理员、团队负责人、安全管理员和普通用户边界验证。
- Session 生命周期和强制重新认证策略。

验收标准：

- 新员工登录后自动进入正确团队。
- 离职或禁用后不能继续使用后台和业务 Key。
- 不需要手工为每个用户创建账号和团队关系。
- 应急账号不参与日常使用，并有独立审计。

## 5.2 真实 Provider 和 Model 探测

至少实现：

- 网络探测。
- 鉴权探测。
- 模型存在性探测。
- 轻量推理探测。
- 流式探测。
- Embedding/Rerank/媒体探测。
- 429、5xx、超时和内容格式错误分类。
- 探测成本和用量隔离。
- 探测失败后的状态、冷却和恢复。

验收标准：

- 健康状态能够反映端到端调用，而不是只反映数据库 `active` 状态。
- 可以区分配置错误、网络错误、凭据错误和上游服务错误。
- 探测失败不会把无关 Provider 误判为故障。
- 探测请求不会无意中产生大量成本。

## 5.3 自动告警

至少实现：

- 错误率窗口计算。
- P50/P95/P99 延迟。
- 429、5xx 和超时。
- Provider 和 Resource 可用性。
- Model 无可用路由。
- 成本突增。
- 额度接近上限。
- 内容安全拦截率异常。
- 告警恢复。
- 去重、抑制、合并和冷却。
- 自动通知路由。

验收标准：

- 创建规则后，规则真的会参与评估。
- 告警生成、通知投递和恢复状态可关联。
- 同一个问题不会持续刷屏。
- 告警通知失败可重试并保留失败原因。

## 5.4 预算执行

建议统一预算资源模型：

- 全局预算。
- 成本中心预算。
- 团队预算。
- 项目预算。
- Key 或用户预算。
- 日/月周期。
- 预警阈值。
- 软限制。
- 硬限制。
- 高价模型限制。
- 超额豁免。
- 时区和币种。

验收标准：

- 页面上的预算值和运行时阻断逻辑使用同一数据源。
- 能明确区分“只告警”和“阻断请求”。
- 并发请求不会绕过预算。
- 失败、取消、重试和后台任务正确结算。
- 预算切换不会错误改写历史账本。

## 5.5 Prompt、Response 和文件数据治理

至少明确：

- 默认是否记录正文。
- 正文保留周期。
- 元数据保留周期。
- 角色级查看权限。
- 项目级数据边界。
- Provider 外发边界。
- Guardrail 服务数据边界。
- 导出审批。
- 访问审计。
- 文件和媒体的清理机制。
- 敏感字段脱敏。

验收标准：

- 普通团队负责人不能查看不属于自己的 Prompt。
- 安全管理员只能在授权范围内查看内容。
- 正文到期后不可从备份、日志和导出中无意恢复。
- 远程 Guardrail 服务的存储和日志策略已获批准。

## 5.6 多副本高可用

正式研发中心部署建议至少使用：

```text
PostgreSQL + Redis + TokenHub 多副本 + 负载均衡 + 集中日志
```

验收标准：

- 任一后端副本停止后，业务请求仍可继续。
- Usage、Quota、审计和任务不会重复或丢失。
- 数据库备份可以恢复。
- 迁移和回滚有演练记录。
- 插件、模型目录和配置在副本之间一致。

## 8. 推荐的目标权限模型

建议采用分层权限：

```text
平台管理员
  管理 Provider、模型、路由、全局配置、凭据和高危操作

安全管理员
  管理 Guardrail、审计、告警和数据访问策略

团队负责人
  管理团队项目、成员、Key 和团队额度

项目管理员
  管理项目成员、Key 和项目模型权限

普通用户
  使用已授权模型，查看个人用量和请求记录
```

### 8.1 平台管理员

可以管理：

- Provider。
- Provider Resource。
- Provider 凭据。
- Model 目录。
- ModelRoute。
- 作用域路由策略。
- 全局额度和预算。
- 成本连接器。
- 数据库和备份。
- 插件。
- 全局系统设置。

高风险操作应进入二次确认或审批：

- 修改 Provider 凭据。
- 开启外部 Provider。
- 发布高价模型。
- 修改全局预算。
- 修改全局 Guardrail。
- 删除账单连接器。
- 恢复数据库备份。

### 8.2 安全管理员

可以管理：

- 内容安全策略。
- Prompt/Response 查看权限。
- 审计和导出。
- 安全告警。
- 数据保留策略。
- 外发 Provider 策略。
- 敏感项目的数据访问边界。

### 8.3 团队负责人

可以管理：

- 本团队项目。
- 本团队成员。
- 本团队 API Key。
- 项目模型申请。
- 团队额度。
- 团队成本查看。
- 团队级告警订阅。

不能管理：

- 全局 Provider 凭据。
- 其他团队数据。
- 全局路由和全局安全策略。
- 全局预算。

### 8.4 普通用户

可以：

- 使用自己有权限的 Project API Key。
- 查看允许访问的模型。
- 查看个人用量。
- 查看自己的请求记录。
- 发起符合流程的模型申请。

不应允许：

- 查看其他用户 Prompt。
- 查看 Provider 凭据。
- 修改团队额度。
- 绕过模型白名单。
- 直接指定未批准的 Provider。

## 9. 推荐的生产架构

## 9.1 试点架构

适用于单团队或少量团队：

```text
浏览器 / SDK
      ↓
TokenHub 单实例
      ├── SQLite
      ├── 本地插件目录
      └── 本地备份
```

建议：

- 仅用于试点。
- 限制团队数量和请求量。
- 明确 SQLite 不用于长期多实例生产。
- 保留定期备份。
- 配置正式 HTTPS 和企业 OIDC。
- 不让普通用户直接接触 Provider 凭据。

## 9.2 研发中心生产架构

适用于多个团队：

```text
业务应用 / SDK / 管理员
          ↓
负载均衡 / Ingress / WAF
          ↓
TokenHub Backend × N
          ├── PostgreSQL
          ├── Redis
          ├── 对象存储
          ├── 集中日志
          ├── Metrics/Tracing
          └── Plugin Distribution
```

建议：

- 使用 PostgreSQL 作为主数据存储。
- 使用 Redis 协调高并发额度和并发 Lease。
- 使用共享或外部存储保存备份、图片和长期文件。
- 使用统一的插件镜像或分发流程。
- 每个副本使用同一个稳定 `TOKENHUB_SECRET_KEY`。
- 通过负载均衡执行健康检查和摘除。
- 将 `/healthz` 和 readiness 检查接入平台监控。
- 将业务指标导出到 Prometheus 或同类系统。
- 将日志和审计事件接入企业日志平台。

## 9.3 高敏感项目架构

对于源代码、生产日志、客户数据和商业机密，建议将项目分成不同数据边界：

```text
普通研发项目
  → 普通 Provider 集合

内部代码项目
  → 获批的内部或私有 Provider

敏感数据项目
  → 私有网络 Provider
  → 更严格 Guardrail
  → 禁止外部 Provider
  → 更短正文保留周期
  → 更严格导出审批
```

不能只依靠项目名称来保护数据边界，必须在路由策略、Provider Resource、网络策略、内容安全和审计层同时落实。

## 10. 分阶段落地计划

## 阶段 0：平台准备

目标：建立平台团队和最小安全基线。

任务：

- 固定 TokenHub 版本，不直接长期使用 `latest`。
- 配置正式域名和 HTTPS。
- 配置企业 OIDC。
- 保留应急管理员。
- 配置 PostgreSQL 方案。
- 生成稳定并安全保存的 Secret Key。
- 设定数据保留和备份策略。
- 明确 Provider 凭据责任人。
- 明确团队、项目和成本中心命名规范。

输出：

- 平台架构图。
- 角色矩阵。
- 数据分类表。
- Provider 清单。
- 模型准入清单。
- 应急恢复手册。

## 阶段 1：单团队试点

目标：验证接入、权限、计量和成本归因。

建议选择：

- 1 个平台团队。
- 1～2 个项目。
- 2～3 个 Provider。
- 少量低风险模型。
- 合成数据或非敏感数据。

验证：

- SDK 接入。
- API Key 发放和吊销。
- 模型白名单。
- Provider 路由。
- 额度策略。
- 内容安全。
- 用量和成本归因。
- OIDC 登录。
- 请求审计。
- Provider 连接测试。

不要在此阶段直接接入：

- 生产客户数据。
- 高敏感源代码。
- 高风险 Agent 工具。
- 未审批的跨境 Provider。

## 阶段 2：研发中心多团队试点

目标：验证组织隔离和成本治理。

建议增加：

- 平台研发团队。
- 算法团队。
- 应用研发团队。
- 每个团队独立 Project。
- 团队级成本中心。
- 团队级额度。
- 模型访问审批。
- 团队级用量看板。
- Provider 作用域策略。
- 团队负责人权限。

重点观察：

- 团队之间是否能看到不应看到的数据。
- 用户离职后 Key 是否及时吊销。
- 团队预算是否准确执行。
- 高价模型是否被误用。
- Provider 失败是否及时发现。
- 成本归因是否稳定。

## 阶段 3：正式研发中心生产

进入正式生产前，至少完成 P0：

- 真实健康探测。
- 自动告警。
- 预算执行。
- 数据治理。
- 企业目录同步。
- PostgreSQL、Redis 和多副本。
- 备份恢复演练。
- 变更审批和审计。
- Provider SLA 和应急预案。

## 阶段 4：平台化和质量运营

目标：从“管理调用”升级为“管理 AI 业务效果”。

建设：

- 质量评测集。
- Prompt 版本。
- 模型版本。
- 用户反馈。
- Tool Call 和 Agent Trace。
- A/B 与 Shadow 流量。
- 业务 KPI 关联。
- 成本优化建议。

## 12. 常见误区

### 误区一：模型能出现在模型列表，就代表一定可用

不正确。模型列表通常反映发布状态和权限，实时请求还会受路由、Provider、Resource、协议、健康、额度和冷却影响。

### 误区二：健康检测通过，就代表模型能正常回答

不正确。当前基础 Monitor 可能只检查对象状态或启用路由，需要真实 Probe 或模型演练场验证端到端能力。

### 误区三：配置了告警规则，就会自动收到通知

不一定。需要确认规则是否被运行时评估、事件是否自动生成、通知是否自动投递。

### 误区四：填写成本中心月预算就能阻断超额请求

不一定。成本中心字段和运行时预算资源不是同一执行路径。

### 误区五：内容安全能检查所有请求数据

不正确。工具参数、任意 JSON、文件、图片、音频和 Provider 响应需要分别确认覆盖范围。

### 误区六：界面显示 SAML/LDAP，就代表已经支持完整 SSO

不正确。生产环境应优先使用已验证的 OIDC/OAuth2 路径。

### 误区七：安装插件就可以扩展 Provider

不正确。当前外部命令型 Provider、Hook、Job 和 Action 不能在生产运行时执行；纯声明式 UI 插件更适合当前外部包能力。

### 误区八：成本报表就是财务结算

不正确。TokenHub 的本地估算、Provider 账单和预计毛利需要与财务系统分开处理。

### 误区九：单机 SQLite 可以直接扩展到研发中心多团队生产

不建议。多团队长期运行应迁移到 PostgreSQL、Redis 和多副本架构。

## 13. 最终建议

如果现在就要开始使用，建议采用以下策略：

### 可以立即做的事

1. 使用 1～2 个低风险研发团队进行试点。
2. 配置企业 OIDC，并保留应急管理员。
3. 使用 Project API Key，不向团队分发 Provider Key。
4. 先开放有限的模型白名单。
5. 为每个团队建立独立 Project 和 Cost Center。
6. 配置额度策略和内容安全策略。
7. 通过模型演练场和真实 SDK 请求验证线路。
8. 手工检查成本归因和审计数据。
9. 对高价模型设置人工审批。
10. 不把当前基础健康检测当作完整 SLA 监控。

### 暂时不要做的事

- 不要直接承接全公司级 AI 统一入口。
- 不要把成本中心月预算当作自动阻断预算。
- 不要将安全策略页面字段全部视为已生效的运行时边界。
- 不要让普通用户配置 Provider 凭据。
- 不要把外部命令型插件作为生产扩展机制。
- 不要在没有数据治理审批的情况下接入客户数据和生产日志。
- 不要用当前账单报表直接替代财务结算。
- 不要长期使用单机 SQLite 承载高并发多团队流量。

### 最优先补齐的五件事

```text
1. 端到端 Provider / Model 健康探测
2. 自动告警、去重、恢复和通知闭环
3. 统一预算模型与运行时超额处理
4. 企业目录同步和权限生命周期
5. PostgreSQL + Redis + 多副本高可用与数据治理
```

### 最终判断

TokenHub 的架构基础适合研发中心 AI 统一接入和治理，尤其适合先建立：

- Provider 统一管理。
- 模型和路由统一管理。
- 团队、项目和 API Key 隔离。
- 基础额度和成本归因。
- 内容安全和审计。

但在自动化监控、预算闭环、企业目录同步、端到端健康探测、质量评测和多实例高可用方面，还需要继续建设。

因此，推荐将落地目标分成两步：

```text
第一步：研发中心 AI 接入、用量和成本治理试点平台

第二步：具备自动监控、预算执行、质量评测和高可用能力的企业 AI 运营平台
```

只有在 P0 能力完成并通过多团队验收后，才建议将 TokenHub 扩大为研发中心的正式统一 AI 生产入口。
